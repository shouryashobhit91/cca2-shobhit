# Hostel Complaint Register

A dynamic web application for logging hostel maintenance complaints and tracking
each one through to resolution. Pages are generated by the server from current
data on every request, and the application is linted, tested, containerised and
deployed automatically by GitHub Actions.

## What it does.

- Raise a complaint against a room, choosing a category and describing the fault.
- Input is validated on the server: the room must look like `204` or `B-204`,
  the description must be at least 10 characters, and the category must be known.
- Every complaint starts as **Open** and moves forward through **In Progress** to
  **Resolved**. It can never move backwards; the server refuses that.
- The header shows live counts and a closure rate, recalculated on each request.
- Complaints can be filtered by status.
- User input is escaped, so markup typed into the form is displayed as text
  rather than executed.

## Routes

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/` | Home page; accepts `?status=Open\|In Progress\|Resolved` |
| `POST` | `/complaints` | Raise a complaint (400 if invalid) |
| `POST` | `/complaints/:id/status` | Advance a complaint (400 if backwards, 404 if unknown) |
| `GET` | `/api/complaints` | JSON list; accepts the same `?status=` filter |
| `GET` | `/api/stats` | JSON counts by status and closure rate |
| `GET` | `/health` | `{"status":"ok","commit":"…"}` — used by the pipeline and by Render |

## Running it locally

```bash
npm install
npm test           # 9 tests
npm run lint
npm start           # http://localhost:3000
```

With Docker:

```bash
docker build -t hostel-complaint-register .
docker run -p 3000:3000 hostel-complaint-register
```

## Pipeline

```
git push
   |
   v
1 Lint ......... npm run lint        every push and pull request
   |
   v
2 Test ......... npm test            9 tests; needs: lint
   |
   v
3 Build ........ docker build        then curl /health inside the container
   |
   v
4 Deploy ....... Render deploy hook  push to main only; needs: build
   |
   v
Live site, footer showing the deployed commit id
```

Each job declares `needs:` on the one before it, so a failure stops the pipeline
there and the later jobs do not run. The deploy job additionally checks
`github.ref == 'refs/heads/main'`, so a pull request is fully checked but never
released.

Installs use `npm ci`, so CI fails rather than silently resolving a different
dependency tree than the one committed in `package-lock.json`.

```
├── app.js                        routes

├── server.js                     listens on process.env.PORT
├── Dockerfile
├── package.json
└── package-lock.json
```

`store.js` and `views.js` are separate from `app.js` so the validation rules and
the escaping can be exercised directly by the tests rather than only through HTTP.

## Deploying to Render

1. **New → Web Service**, connect this repository.
2. Language **Docker** (it will use the Dockerfile, which installs with `npm ci`).
3. Health check path: `/health`.
4. Turn **Auto-Deploy off** — the pipeline triggers the deploy instead, so that
   nothing ships until the lint, test and build jobs have passed.
5. **Settings → Deploy Hook**, copy the URL.
6. In GitHub, **Settings → Secrets and variables → Actions → New repository
   secret**, name it `RENDER_DEPLOY_HOOK` and paste the URL.

Render sets `RENDER_GIT_COMMIT` automatically, which the footer and `/health`
both read, so the running commit is visible on the live site.

## Notes

Complaints are held in memory, so they reset when the service restarts. That is
deliberate for this assessment: the focus is the delivery pipeline rather than
persistence. Adding a database would mean replacing `store.js` and nothing else.
